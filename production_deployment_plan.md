# BQ Orchestrator: Production Deployment & Registry Publication Plan

This document provides the complete, production-grade deployment architecture, sizing guidelines, and registry publication steps to deploy the **BQ Orchestrator Agent** to **Vertex AI Agent Runtime** (Reasoning Engine) and register it in the **Gemini Enterprise Agent Registry**.

---

## 🏗️ 1. Infrastructure & Service Account Provisioning

The project contains a complete, declarative Terraform design in `deployment/terraform/single-project/`. This provisions the required service accounts, IAM bindings, logging buckets, and enables the necessary Google Cloud APIs.

### Key GCP IAM Roles Required for the Agent Service Account (`app_sa`):
*   **`roles/aiplatform.user`**: Required for the agent to call the underlying Gemini LLMs.
*   **`roles/logging.logWriter`**: Required for writing runtime telemetry and logs to Cloud Logging.
*   **`roles/storage.objectViewer`**: Required to read the downstream Agent Cards from Google Cloud Storage (GCS).

### Execution Steps:
1. Initialize and run Terraform to provision the cloud infrastructure:
   ```bash
   cd deployment/terraform/single-project/
   terraform init
   terraform apply -var-file=vars/env.tfvars
   ```

## 🚀 2. Deploying to Agent Runtime

Vertex AI Agent Runtime is a fully managed, auto-scaling execution environment for Python ADK agents.

### Downstream Agent Cards Configuration (CI/CD Safety):
Since the card files are excluded from our public GitHub repository, we store the cards in a secure GCS bucket in your GCP project and reference them via GCS URIs:
*   `gs://<your-secrets-bucket>/nba_stats_agent_card.json`
*   `gs://<your-secrets-bucket>/mlb_club_fan_agent_card.json`

At startup, the upgraded `load_agent_card()` helper in `app/agent.py` will automatically fetch these files from GCS using the running service account's default credentials (ADC).

### Production Sizing & Scaling Guidelines:
*   **GIL Process Parallelism**: In Python, execution is GIL-bound. Each worker process utilizes exactly 1 core. To maximize throughput under load, we scale the CPU and worker counts together: `--cpu 2` and `--num-workers 2`.
*   **Memory Safety**: Concurrent requests consume memory for context, history, and buffers. To prevent Out-Of-Memory (OOM) crashes, we allocate a safe, large memory envelope: `--memory 8Gi` and set container concurrency to `16`.

### Deployment Command:
Run the deployment from your terminal (using the PyPI index bypass):
```bash
UV_DEFAULT_INDEX=https://pypi.org/simple UV_INDEX=https://pypi.org/simple UV_EXTRA_INDEX_URL="" \
agents-cli deploy \
  --project YOUR_PROJECT_ID \
  --region us-east1 \
  --service-name bq-orchestrator \
  --service-account YOUR_APP_SERVICE_ACCOUNT_EMAIL \
  --update-env-vars "NBA_AGENT_CARD=gs://YOUR_SECRETS_BUCKET/nba_stats_agent_card.json,MLB_AGENT_CARD=gs://YOUR_SECRETS_BUCKET/mlb_club_fan_agent_card.json" \
  --cpu 2 \
  --memory 8Gi \
  --num-workers 2 \
  --concurrency 16 \
  --min-instances 1 \
  --max-instances 10
```

## 📇 3. Registering with Gemini Enterprise (Agent Registry)

Publishing your agent to the **Gemini Enterprise Agent Registry** exposes the Orchestrator as a registered agent, allowing upstream Master Routing agents to discover, invoke, and delegate tasks to it.

### Prerequisites:
1. Establish a **Gemini Enterprise App** in your Google Cloud Console under `Gemini Enterprise` -> `Apps`.
2. Retrieve the app's full resource ID:
   `projects/<PROJECT_NUMBER>/locations/global/collections/default_collection/engines/<GEMINI_APP_ID>`

### Registry Publication Command:
Since we are exposing the Orchestrator via the A2A protocol, we use `--registration-type a2a`. The command automatically reads the `deployment_metadata.json` file generated by the deploy step to resolve the runtime ID and register the agent:
```bash
UV_DEFAULT_INDEX=https://pypi.org/simple UV_INDEX=https://pypi.org/simple UV_EXTRA_INDEX_URL="" \
agents-cli publish gemini-enterprise \
  --registration-type a2a \
  --gemini-enterprise-app-id "projects/YOUR_PROJECT_NUMBER/locations/global/collections/default_collection/engines/YOUR_GEMINI_APP_ID" \
  --display-name "BQ Orchestrator" \
  --description "Exposed A2A router agent that assesses and routes sports analytical queries to NBA Player Stats and MLB Fan Experience Conversational Analytics agents."
```

## 🎫 4. Generating the Orchestrator Agent Card for Upstream Integration

To integrate this BQ Orchestrator with an upstream **Master Routing Agent**, the master routing team needs your Orchestrator's **Agent Card**.

Once the BQ Orchestrator is deployed to Agent Runtime:
1. The Agent Runtime service automatically and dynamically hosts the Orchestrator's Agent Card at the following public endpoint:
   `https://<agent-runtime-endpoint-url>/a2a/app/.well-known/agent-card.json`
2. You can retrieve the URL from the deployment metadata or print the card locally by running:
   ```bash
   python3 -c "import asyncio; from app.agent_runtime_app import agent_runtime; print(asyncio.run(agent_runtime.agent_card.model_dump_json(indent=2)))"
   ```
3. Give this URL or the printed JSON card to the Master Routing Agent team. They can register it in their sub-agent configuration as a `RemoteA2aAgent`, allowing their master router to seamlessly hand off NBA and MLB analytical queries directly to your Orchestrator!

## 💡 5. Critical Production Considerations

### 🛡️ A. Secret & Key Management
*   Never store GCP Service Account Keys, API keys, or database passwords in your Git commits or environment variables. 
*   Always utilize **GCP Secret Manager** or **IAM Role-based Access Control** (such as Workload Identity and Application Default Credentials) to manage and grant secure runtime access.

### 💰 B. BigQuery Regional Co-location
*   **Egress Cost Warning**: Transferring data across different cloud regions incurs heavy inter-region egress charges.
*   **Co-location Rule**: Ensure that the Reasoning Engine's deployment region (configured in `agents-cli-manifest.yaml` and your Terraform files, e.g., `us-east1`) is **exactly co-located** with your BigQuery datasets storage projects. 

### 📊 C. Telemetry & Observability
*   The project is pre-configured with **OpenTelemetry** support (`app/app_utils/telemetry.py`). 
*   Ensure prompt-response logging is enabled in production to capture conversation traces in a BigQuery logging table for post-launch analytics, performance monitoring, and model fine-tuning.
